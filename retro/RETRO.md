# RETRO

> 每條寫成可直接貼進 writer prompt 的**約束句式**（背景一句、約束一句），不寫敘事——retro 的消費方式是前置進 prompt 硬性約束區（eval-flow 循環 step 1），不是開工前通讀。

- 2026-07-15［hook／bugfix］`eval_gates.py` 的 `MANIFEST_RE` 誤把 `run/<id>.test_baseline.json` 當 manifest 攔 commit——排除規則只寫在單一呼叫點的 `endswith(".eval.json")`，新增衍生檔種類時沒有同步。**約束：以 pattern 判檔案身分時，排除規則必須寫進 pattern 本身（單一判定點），不可散落在呼叫點用 endswith 補丁；新增衍生檔命名時，先查所有以檔名 pattern 分流的地方。**
- 2026-07-16［流程設計／skill 規則投放路徑／2026-07-16-review-writeahead-fixture-rules］test-strategy skill 的 Mutation self-check 新增規則時，把重放 sabotage 的責任指派給 code-reviewer——但 reviewer 定義明訂只讀不寫（sabotage 需改檔）、且 reviewer 呼叫時完全不載入 test-strategy skill（無投放路徑），導致規則寫了等於沒生效。根因是新增跨角色規則時只驗證「內容對不對」，未驗「收件人讀得到嗎（投放路徑）」與「收件人有權限做嗎（角色約束）」。**約束：在 skill 或 agent 定義中新增執行步驟時，必須先確認兩點再落筆：（1）該步驟所在的文件是否在執行者的載入路徑內；（2）執行者的角色定義是否允許執行所需操作——任一不符則改換收件人，不可只改措辭。**
- 2026-07-17［test_baseline.py／外部輸出解析／2026-07-17-writer-scoped-tests］`git status --porcelain` 的輸出被當作純文字字串拼接進 `shell=True` 指令、並以 `rest.strip()` 取檔名——兩處都憑「常見格式印象」處理，未先查閱 porcelain 的完整邊界表示（C-style 引號、NUL 分隔、rename 兩段），導致含空白或特殊字元的檔名造成路徑污染與 shell 注入。**約束：消費任何外部工具的文字輸出（git、shell、CLI）前，必須先查閱該格式的官方規格確認分隔符與跳脫表示，再選擇對應安全的解析 API（如 `--porcelain -z` + NUL split、`shlex.split`、list argv），不可直接字串拼接或 strip 取路徑。**
- 2026-07-17［test_baseline.py／測試邊界覆蓋／2026-07-17-writer-scoped-tests］`git_changed_files` 的解析邏輯（rename、deleted、含空白、含 `$` 檔名）零測試；另一條測試建了 runner/sentinel/capture.sh fixture 卻全未在測試邏輯中使用，實際只斷言純函式字串——名為整合測實為假整合測，根因是只寫 happy path 且 fixture 建立後沒驗證確實被觸發。**約束：寫解析外部工具輸出的函式時，測試必須覆蓋至少：正常路徑、含空白路徑、含特殊字元路徑、rename／deleted 邊界各一條；整合測試中建立的每個 fixture（runner、sentinel、capture 腳本）必須在斷言中直接可驗證其被呼叫，否則刪除 fixture 改寫純單元測。**（候選 lint 規則：偵測測試函式內有 `os.makedirs`／`shutil` 但無對應 assert path 或 mock call 驗證的情況）
- 2026-07-29［流程設計／機制上線前的端到端實跑／2026-07-28-gate-worktree-root＋parallel-run 首次實跑］同一天兩次同型失效：`eval_gates.py` 的 worktree root 解析、與 `parallel-run` 的背景 agent 啟動契約，都是「文件寫完整、測試給綠燈、宣告可用」但從未被真正執行過一次的機制；兩者都在第一次實跑的**第一步**就失敗。前者更危險——失敗是靜默的（worktree 內 commit gate 完全不檢查憑據而照常放行），且有一支名為 `check_worktree_isolation.sh` 的測試以直接 import 呼叫函式的方式繞過實際執行路徑，給出 4/4 綠燈的假保證。根因是驗收只問「有沒有寫完、測試有沒有綠」，沒有問「這條路被端到端走過嗎」。與 2026-07-16 的「投放路徑」條同源（都是未驗證收件人端真的收得到），但作用在執行契約而非規則文字。**約束：新增或修改「跨進程／跨工作區／跨 agent 的執行契約」（worktree 啟動方式、hook 投放路徑、subagent 的工具與 cwd 前提、agent 間的交付格式）時，DoD 必須包含一次真實端到端執行的證據——實際啟動該路徑並貼出可觀察的外部結果（exit code、被攔截的訊息原文、實際 cwd、產出檔案）；以直接呼叫內部函式繞過該契約實際執行路徑的單元測試，不構成驗收證據，宣稱「已實測坐實」前必須先確認測的是哪一條路。**
- 2026-08-07［skills／task-decomposition／跨文件語義相容性／2026-08-07-blocking-edges］主 flow 在 task-decomposition skill 新增 frontier 排程語義（depends 與 [P] 的允許組合）時，做了 RETRO 前置但未 grep eval-flow 對同一關係的既有規定，導致兩份文件對「標 depends 的 item 可不可以同時標 [P]」下相反指令（新句允許、eval-flow:310 禁止），直到 reviewer 的相容性檢查才攔到；根因是「本 run scope 不動消費端」被誤讀為「消費端與本 run 無關」，正確讀法是「正因 scope 排除修改消費端，才更必須先讀它對同一語義的既有規定，以此設定新句的邊界」，兩種讀法的結果剛好相反（疏忽）。**約束：在任何 skill 或流程文件中新增定義某語義關係（兩個欄位或標記之間的允許組合、執行順序、互斥規則）的規則時，必須先 grep 全 repo 找出所有對同一關係有現行規定的文件，逐一確認新句與之不矛盾——消費端文件（如 eval-flow）的既有規定是執行契約、優先級最高；即使本 run 的 scope 明確排除修改消費端文件，此盤點仍是寫新句的前置步驟、不可省略。**
- 2026-07-30［流程設計／清單與規則的單一枚舉點／2026-07-30-flow-doc-gaps］同一份「該做哪些事」的枚舉（收尾要 git add 的檔案清單）被複製到三處各自維護（eval-flow step 6、Tier 1 精簡路徑、[P] fan-out 節），且與另一份 skill（test-strategy）對同一件事的規定不一致，實際造成兩個 run 的 baseline 檔靜默遺失——漏掉不會有任何 gate 或錯誤訊息，只在剛好要刪 worktree 且事前檢查時才發現。更關鍵的是：**為修這個缺口而開的 run 自己重演了同一模式**——只改到 step 6，另外兩處同義敘述當場漏改，DoD 七條全綠仍未攔住（DoD 只驗「我打算做的有沒有做到」，驗不了「我該做的有沒有想全」），最後靠 reviewer 的完成度節抓出。與 2026-07-15「以 pattern 判檔案身分時排除規則須寫進 pattern 本身」同源，但作用在跨文件的枚舉清單而非單檔的判定式。**約束：任何「該做哪些事／該包含哪些項」的枚舉清單，全 repo 只准有一個枚舉點，其他位置一律以指向式引用（「依 X 的清單，減去 Y」）而非重列；新增或修改此類清單時，先 grep 全 repo 找出所有同義枚舉並一次收斂到單一點——修一處而留其他重列版本，等同沒修。以指向式引用時亦不得 inline 附上推導結果，那是另一份會漂移的重列。**
