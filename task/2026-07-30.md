## 背景（自足，不依賴對話）

2026-07-29 首次實際執行 `parallel-run`，暴露其 skill 描述的操作方式與 harness 實際支援的能力不一致，共五處。實測證據：

1. **啟動契約不成立**：skill 步驟 5–6 寫「主 session `git worktree add` 建 worktree → spawn 背景 agent，工作目錄固定在自己的 worktree」。實測兩支背景 agent 皆於第一步失敗——從 repo root 啟動的 subagent cwd 被釘死，`EnterWorktree` 回：
   > Cannot enter worktree: the current working directory … is the repository root, not an isolated worktree — switching is only available to sessions whose working directory is inside a worktree of this repository.

   可行的方式是 `Agent(isolation: "worktree")`：harness 建立 `.claude/worktrees/agent-<id>/` 並**在啟動時釘定** agent 的工作目錄。釘定是 gate 正確生效的前提——hook 依 tool call 的實際 cwd 解析所屬工作區，agent 若用 `cd` 進 worktree，cwd 仍被判為主工作區，gate 會套用到錯的 repo。
2. **branch 命名不由主 session 決定**：`isolation: "worktree"` 的 branch 名稱由 harness 指派（`worktree-agent-<id>`），不是 skill 假設的 `feat/<run_id>`。步驟 7、8.1、8.4、8.5 及重用清單皆以 `feat/<run_id>` 書寫，須改為「agent 回報的 branch」。
3. **worktree 起點不是主線 HEAD**：harness 的 worktree 從 `origin/<預設分支>` 切出，會少掉主線上未 push 的 commit（實測差 2 個 commit，導致需求前提不成立）。agent 起手須 `git merge main` 同步。
4. **harness worktree 帶 lock**：步驟 8.5 的 `git worktree remove` 對其失效（實測 `--force` 仍被擋，提示需 `-f -f` 或先 unlock）。強拆可能破壞 harness 狀態，屬應回報而非硬幹。
5. **批次層 baseline 無 manifest 可讀 `test_command`**：步驟 8.4 說該快照「不屬於任一 run」，但 `test_baseline.py` 的 single-source 設計預設從 manifest 讀，故須手動帶 `--cmd`（實測第一次呼叫即失敗）。

另附帶一處觀察：步驟 8.3「後合者先同步」在 worktree 側執行 `git merge main`，其後將該 branch 合入 main 會產生名稱為 `Merge branch 'main' into worktree-agent-…` 的 merge commit。無害但 log 語意反向，值得註明。
