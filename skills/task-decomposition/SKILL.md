# Task 分拆框架

> 本 skill 由 **`task-decomposer` subagent** 載入使用（Eval Flow 前置 1，條件派工超門檻時呼叫；≤2 tasks 且 ≤8 items 含界由主 flow 直建，不派此 agent）。主 flow 不直接跑此 skill，而是委派該 agent，由 agent 涵蓋本 skill 作為指令內容。
>
> 本文件中標 `（R-NNN）` 的規則源自真實失敗——改或刪該規則前，先讀 retro/RETRO.md 對應條目確認變更不會重開該失敗。

**把 Spec 拆成「小到可以一次寫對、獨立可驗收」的單位。粒度失控是 eval flow 失敗與 scope 偏移的頭號成因。**

輸入：run manifest `run/<run_id>.json`（由 `eval_state.json.run_id` 定位）的 `spec_path`（**Spec**）。**一律從 manifest 讀路徑，不自行以日期 / 檔名重組**。`usage_report_path` 維持 `null` 屬正常——不以此欄為 `null` 中止；若主 flow 曾具名問題觸發 `usage-analyzer`／`impact-analyzer`，答案已併入 Spec，拆分時一併參考。
輸出：`task/YYYY-MM-DD.md` 內的 task 清單，每個 task 展開為 ≤5 個 item，每個 item 對映一個使用情境、可獨立 `git diff` 審查。

## 硬性上限（違反即須再拆，不可協商）

| 層級 | 上限 | 超過時的動作 |
|---|---|---|
| **每個 task** | 最多 **5 個 item** | 拆成多個 task（通常沿功能切片或分層切） |
| **每個 item** | 預估最多 **300 行 code** | 拆成多個 item（沿檔案 / 職責 / happy-path vs 邊界切） |

上限是為了讓每個 item 的 `git diff --cached` 小到 code-reviewer 能一次讀完審完。**300 行是「新增 + 修改」的總和，不含自動生成的 lockfile / migration 樣板。**

**驗證方式**：先依 test-strategy「依變更選擇驗證」規劃。純設定 item 的 DoD／契約綁定設定與操作證據，不強制拆測試 item；混合任務各部分綁適用證據。下方單元／整合與 fixture 要求僅適用需要新增或修改的程式測試。

安裝、遷移或恢復類 item 的既有契約須說明重跑及中斷後重跑的預期結果：可安全重跑、從已完成位置接續，或明確拒絕並提供恢復方式。依需求選擇，不一律要求冪等；沿用適用證據與契約行數預算，不因此擴成全面併發改造或新增固定驗證輪次。

**驗證要求（Tier 2）**：每條需求綁定適用證據。優先沿用既有相關測試；只有證據缺口才補最小黑箱行為測試，不要求每個實作 item 新增單元測試。
- 跨 item 行為須有整合層證據；既有整合測試足夠時沿用，不固定新增整合測試 item。reviewer 指出具名盲點時才補針對驗證，見 test-strategy。
- DoD 沒有適用證據的新行為 item，交付前自檢不通過即補齊驗證方案；不為此強制拆新測試 item
- 循環 step 5 核對適用證據與剩餘缺口；Tier 1 仍可用自動化測試或實際運行驗證
- 測試類 item（含各實作 item 的單元測試與整合測試 item）的 DoD 另附兩條硬要求，交付前自檢不符即重拆：
  - **fixture 逐區塊附 producer 行號依據**（fixture 的每個資料區塊須以註解標明「依據 &lt;producer 檔:行&gt;」，證明與 producer 實際輸出對齊，防漂移後消費路徑零覆蓋且全綠）
  - **fixture 為測試實際載入的 single source**（不得另存一份測試不讀的副本）

**行為契約表（DoD 的測試依據，Tier 2 硬性）**：每個引入新行為的實作 item（含設定），DoD 須附「輸入 → 預期可觀察效果」對照表——2~4 條核心行為＋**至少 1 條邊界輸入**。

- **邊界的機械判準：與核心行為走不同回傳／副作用分支的輸入**（不同 error code、提前 return、不同 side effect；典型如空值、特殊字元、越界值）
- 「可觀察效果」＝回傳值＋副作用（DB 寫入、檔案、對外呼叫），**不含內部實作細節**
- 此表是需求與驗證的依據：每條 row 須有適用證據，可沿用既有測試、實跑或設定檢查；不要求逐 row 新增測試或斷言。writer 發現未定義行為時先建議補表，不自行創造需求
- 此表也是測試失敗時的仲裁基準（判「code 錯還是測試錯」**以 DoD 中的行為契約表為準**，與 code-writer 測試管轄規則的 DoD 仲裁同義）。表未涵蓋但應測的邊界 → 回頭補進表再測（表可增補，single source 不變）；本規則禁止的是繞過表、對實作細節或未定義行為做臆測性斷言
- 契約表由拆分者（另一顆腦）從情境報告推導，不是 writer 對需求的自我詮釋——這是「自產自證」變「他證」的關鍵
- **組合 row 規則**：item 有 ≥2 個可獨立取值的輸入面（旗標×模式、參數×路徑、選項×子命令）時，契約表除既有「至少 1 條邊界輸入」外，須含至少 1 條組合 row（兩個輸入面同時取非預設值的可觀察效果）；此類 row 需求超額時比照下方「輸出格式」節行數預算——以再拆 item 消化、不砍邊界覆蓋

## 功能移除的測試三分法與測試同步段

需求刪除功能或有意改變既有行為時，拆分前必讀 [既有行為與測試分流](references/behavior-changes.md)；Tier 1 由主 flow、Tier 2 由拆分者核對，並將適用規則與對照表交付執行者。

**多處投放語義檢查（拆分期檢核）**：item 需求是把**同一句規範文字**投放到 **≥2 個異質語境**（多個 agent 定義、多個 skill）時，拆分期（Tier 2 由拆分者、Tier 1 由主 flow）須逐語境核對該句的關鍵詞在各語境無語義碰撞，碰撞則措辭加區隔詞（R-006）。

## Step 1：以使用情境為切割主軸

先把使用情境報告的每個情境列出來。**預設一個核心情境 → 一個 task**，因為情境天然對映「一段可獨立驗收的行為」。

- happy-path 情境 → 主 task
- 邊界 / 異常情境 → 若處理邏輯 <100 行，併入該情境的主 task 當獨立 item；若成體系（例如整套錯誤處理 / 重試 / 併發控制）→ 獨立 task
- 跨情境的共用基礎（DB schema、共用 client、型別定義）→ 抽成前置 task，標為其他 task 的依賴

**檢驗問題：** 這個 task 對應的使用情境，能不能在不碰其他情境的情況下 demo 給使用者看？不能 → 切割線畫錯了。

## Step 2：估算每個 item 的行數

在寫 code 前估行數，用「檔案 × 職責」的粗估法。以下為單一 item 的參考量級：

| 產出類型 | 粗估行數 | 備註 |
|---|---|---|
| 新增 DB model / migration | 30–80 | schema 複雜則獨立成 item |
| 新增 API endpoint（route + handler + validation） | 80–150 | 一個 endpoint 一個 item |
| 新增 service / 商業邏輯模組 | 100–250 | 超過 → 沿函式職責再拆 |
| 新增前端元件（表單 / 表格 / 互動） | 100–250 | 元件 + 狀態 + API 串接常超標，拆分層 |
| 設定 / wiring / DI 註冊 | 20–50 | 可併入相鄰 item |
| 該 item 的單元測試 | **契約表 row 數 × 10–20 行**（行為數驅動，非實作行數驅動） | **併入該 item 估算**（測試隨實作，見上「測試要求」）；細則見表下附註 |

- 單元測試估算附註：獨立成 item 的只有整合測試。測試預算綁契約 row 數、不綁實作行數（200 行實作若只有 3 條 row，測試就該是 ~30–60 行，不是 100–200 行）——綁實作行數會變相鼓勵灌測試

**校準：** 上表是「邏輯骨架」的量級，實際 diff 還有 docstring、錯誤路徑、常數表——naive 粗估**系統性低估 2–3 倍**。申報行數 = 表列量級估出的數 **×2**。寧可高估觸發再拆，不可低估躲 300 行上限（低估會讓軟上限形同虛設）。

×2 校準後的數字**同時餵兩個判斷**：≥150 行觸發 worktree fan-out（`[P]` 門檻下限）、>300 行觸發再拆（上限）——兩者並存不衝突，一個數字各自對到對應閾值。

**估算捷徑：** item 觸及的檔案數 × 每檔平均行數（含測試檔）。觸及 **>3 個檔案**，幾乎必然超標或職責過雜 → 拆。

**檢驗問題：** 如果現在就開一個 code-writer 去寫這個 item，產出的 `git diff` 會不會超過一個螢幕能審完的量？會 → 拆。

## Step 3：判斷 item 拆分方向

單一 item 超標時，依序嘗試以下切法（由上而下優先）。**注意：單元測試不是切割線**——把測試從實作 item 抽走會讓新行為裸奔到整合階段，測試要跟著它驗證的實作一起走：

1. **分層** — 同一情境的 backend / frontend / DB 拆成不同 item（各自帶各自的測試，也順便解鎖平行化）。
2. **職責 / 函式群** — 一個 service 裡多個獨立函式群 → 各自成 item。
3. **happy-path vs 邊界** — 先把正常流程做成一個 item，錯誤處理 / 重試 / 併發保護做成另一個 item。
4. **CRUD 拆讀寫** — Create/Update（有副作用、需驗證）與 Read（查詢、序列化）拆開。

task 超過 5 個 item 時，依序：功能切片 → 分層 → 前置基礎抽離。

## 推理密度（演算法密集 item 須附偽代碼骨架）

行數之外的第二軸：**推導負擔**。機械判準：item 規格含 **≥3 步、步驟間有資料流依賴**的演算法程序（多步解析、座標聚類、狀態機）＝演算法密集。

此類 item 只給散文步驟不合格——**Spec（Tier 2）或 manifest `spec_inline`（Tier 1；主 flow 直建 task 檔時同樣適用）須附偽代碼骨架**：函式切分、各函式輸入輸出、核心資料結構。item DoD 只指向骨架所在（實作內容不進 DoD，沿「禁止內嵌實作內容」規則）。

原則：**code-writer 是執行者，不是推導者**。「散文規格 → 程式結構」的推導若留到執行期，全部落在 writer 的 thinking（R-017）。推導成本要花在拆分期（產出可審的骨架），不花在執行期（燒滿即死、無殘留物）。

## 寬幅重構例外（expand–contract，唯一不縱切的拆法）

機械式變更跨全庫且任何縱切片都無法獨綠時，拆分前必讀 [寬幅重構](references/wide-refactor.md)，核對完整適用判準與三段序列。

## Step 4：標註平行化與依賴

- **`[P]` 可平行化**的條件（兩者都要成立）：
  - 不共用檔案（無 merge 衝突面）
  - 無資料依賴（不需要另一個 item 的產出當輸入）
- 有依賴的 item 明確標 `depends: <item id>`。前置基礎 task（DB schema / 共用型別）幾乎都是其他 item 的依賴，不可標 `[P]`。
- **frontier 排程規則（供下游主 flow 排程，僅管循序執行）**：item 的可開工判準是「其 `depends` 全部完成」，**不是編號順序**——當前所有可開工 item 的集合即 **frontier**，循序執行時主 flow 從 frontier 取工即可，編號只是識別不是序（depends 已全部完成的 item，不必等編號在前的無關 item）。
  - `depends` 與 `[P]` 的分工：`depends` 描述依賴圖的**邊**（誰擋誰），`[P]` 描述無依賴 item 間**可同時派工**（無檔案交集、無資料依賴——即上述兩條件）
  - **既有互斥規則不變**：標 `depends` 的 item 不標 `[P]`——fan-out 的 prep 段以此判進循序段（見 `eval-flow` skill「Tier 2 [P] fan-out」；worktree 隔離下，依賴未落地的 item 進不了並行批）

**worktree fan-out 門檻（供下游主 flow 判斷）**：標 `[P]` 的 item，當**≥2 個且各自估計 ≥150 行**（以本檔 `~<行數>行` 欄的 ×2 校準值為準）時，主 flow 於 Tier 2 執行時各開 git worktree 並行（見 `eval-flow` skill「Tier 2 [P] fan-out」節）。

不足此門檻則 `[P]` 退回主 worktree 循序執行。估計不準時保守處理——估不準即不 fan-out。

**檢驗問題：** 兩個標 `[P]` 的 item，同時派兩個 code-writer 去寫，合併時會不會撞到同一個檔案？會 → 不是 `[P]`。

## 輸出格式（寫入 `task/YYYY-MM-DD.md`）

```
# Task — <Spec 名稱>  (created: YYYY-MM-DD HH:MM)

## Task 1: <對映的使用情境名稱>
- 依賴: 無
- [ ] 1.1 <item 描述＋單元測試>  ~<估計行數（含測試、已 ×2 校準）>行  files: <實作路徑>, tests/...
      DoD: <可驗收條件>  情境: <usage 報告中的情境 id>
      契約: <輸入> → <可觀察效果>；<輸入> → <效果>；[邊界] <怪輸入> → <效果>
      退場: <測試檔::測試名, …>｜none
- [ ] 1.2 [P] <item 描述＋單元測試>  ~<行數>行  files: <路徑>, tests/...
      DoD: ...  情境: ...
- [ ] 1.3 整合測試（跨 item）（僅補證據缺口）  ~<行數>行  files: tests/...
      DoD: <整合層涵蓋哪些情境；適用證據與尚缺的行為驗證>

## Task 2: <另一個情境>  depends: Task 1
- [ ] 2.1 ...
```

- item 完成後標 `[x]`
- 每個 item 必含四要素：**估計行數、影響檔案、DoD、對映情境**。缺任一 → 交付前自檢不通過即重拆
- **`退場:` 行（測試退場規則）**：每個實作 item 必含——列本 item 作廢行為對應的**既有測試**（`測試檔::測試名`，多筆逗號分隔），無則寫 `none`（行數預算計 1）。Spec／spec_inline 含作廢舊行為清單（測試同步段）或功能移除（三分法 A 類）時，對應 item 的退場行**必填且不得為 `none`**——寫 none 即交付前自檢不通過。writer 須在**同一 run** 刪除列出的測試；獨立審查核對已消失（存在性核對住 task-verifier 定義）。動機：測試只增不刪是膨脹主因
- **item 行數預算（校準值，實測後可調）**：每 item 全部內容（含 DoD 與契約表）≤ **12 行**——**計數以邏輯單元為準**：描述、每條 DoD、每條契約 row、情境各計 1，不論排版折疊成單行或逐行展開；DoD ≤ **5 條**、每條為一句可驗斷言（grep／指令／可觀察效果；排版單行分號串接或逐行皆可）
  - 超標＝實作細節誤入 DoD 的訊號，瘦身或再拆 item（12＝描述 1＋DoD 上限 5＋契約表上限 5＋情境 1 的算術和；5＝合規 DoD 壓縮實測殘量 3–6 的上緣）
  - 契約 row 需求超過 5 條時以**再拆 item** 消化，不得為湊預算砍邊界覆蓋（上方「至少 1 條邊界」為硬性）
- **禁不可驗評價詞（驗收語紀律）**：DoD 與契約 row 不得以評價詞作為驗收語——「正常」「完善」「正確」「妥善」「良好」「穩定」「優化」「合理」等無機械判準的詞，除非同句緊跟判準（例「正常＝exit 0 且 stdout 含 X」）
  - 評價詞是上條「可驗斷言」的高頻逃逸口：句子看似驗收條件，實際無法對照任何輸出判真偽
- **step5 憑據記號**：DoD 條目的憑據本質上只能由循環 step 5 實跑產生（視覺呈現、實機行為、部署後操作驗證——step 3 審查時點必然無憑據可核）時，條目尾標 `[憑據:step5]`
  - 記號定義住本 skill（單一枚舉點）；消費規則住 task-verifier 定義（checker 記 🔍 step 5 待驗、不計升級）與 eval-flow 循環 step 5（主 flow 收口核對）
  - **僅限實跑類憑據**——可用測試斷言、grep、靜態檢查驗的條目不得標（標了等於把可自動驗的事推給人工，checker 對憑據的核對就被架空）
- **禁止內嵌實作內容**：要寫進目標檔的替換全文、程式碼片段不得放進 DoD——精確措辭重要時，住 Spec（Tier 2）或 manifest `spec_inline` 補註（Tier 1），DoD 只留指向與斷言
- **自足性＝指向式引用**：「自足」是讀 task 檔＋其引用的 spec／usage／impact 檔即可接手，不是全部內嵌——情境以 id、風險與慣例以報告節名指向，不重述報告內容（task 檔 header 註記同理）

## 反模式（命中即 reject 重拆；前文硬性規則同樣適用）

- item 沒有估計行數，或估計明顯灌水以躲過 300 行上限（含未套 ×2 校準的系統性低估）；一個 item 觸及 >3 個檔案還宣稱 <300 行
- task 塞滿 5 個 item 只為了不開新 task（湊數，不是內聚）
- item 描述是「實作 X 功能」這種無邊界的整包，無法對映單一情境或 DoD
- 把邊界 / 異常處理整包吞進 happy-path item，讓 diff 爆量
- 標 `[P]` 但兩個 item 共用檔案或有資料依賴
- 前置基礎（schema / 共用 client）沒抽出來，導致多個 item 重複定義
- 寬幅重構硬拆縱切片、或無 expand 緩衝的一次性大爆炸替換——該走 expand–contract 序列（見該節）
- task 檔重述 Spec／usage／impact 報告已有的內容——自足性靠指向式引用達成，重述使 task 檔膨脹且兩處易漂移

## 範例：Spec「廠商付款申請單新增部分沖銷」

使用情境報告（節錄）：情境 A 財務登記部分付款；情境 B 系統更新未結餘額；情境 C 超額時拒絕登記。B 的共用計算先成前置 task，A、C 依賴它。以下示範 C 的完整 item；其他 item 使用同一輸出格式。

```
## Task 2: 部分沖銷登記 API  depends: Task 1
- [ ] 2.2 超額沖銷防呆與適用測試  ~140行  files: routes/settlement.py, tests/test_settlement_api.py
      DoD: 超額回 422 且不寫入 settlement；沿用或補齊契約證據  情境: C
      契約: 金額=餘額 → 201、餘額歸零；金額<餘額 → 201、扣除該金額；[邊界] 金額>餘額 → 422、不寫入 settlement；[邊界] 金額=0 → 422、不寫入 settlement
      退場: none
```
