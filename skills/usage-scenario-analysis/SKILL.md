# 使用情境分析框架

> 本 skill 由 **`usage-analyzer` subagent** 載入使用（Eval Flow 前置 2）。主 flow 不直接跑此 skill，而是委派該 agent，由 agent 涵蓋本 skill 作為指令內容。
>
> 本文件中標 `（R-NNN）` 的規則源自真實失敗——改或刪該規則前，先讀 retro/RETRO.md 對應條目確認變更不會重開該失敗。

**在寫任何 code、拆任何 task 之前，先窮舉「這個功能會被誰、在什麼情況下、怎麼用」。使用情境沒盤全，後面拆出來的 task 就是殘缺的；歧義沒攤開，就會拿錯誤的假設一路寫下去。**

這份報告有兩個下游責任：（1）它的**情境 id** 是 `task-decomposition` 每個 item 對映的錨點；（2）它是**唯一的前置 HITL gate**——使用者在此確認情境與假設，確認後才准分拆。因此報告要為「使用者快速確認」而寫，把不確定的地方主動攤成開放問題，而不是替使用者假設。

---

## 輸入 / 輸出

- **輸入**：run manifest `run/<run_id>.json`（由 `eval_state.json.run_id` 定位）的 `spec_path` 指向的 **Spec**。`spec_path` 與 `spec_inline` 皆空 → 中止並回報（前置 0 未完成）。
- **輸出**：使用情境報告存檔於 `usage/<run_id>.md`；使用者確認後，把該路徑寫回 manifest 的 `usage_report_path`。
- **HITL gate（硬性）**：報告產出後**必須回報使用者確認**，特別是「開放問題」要逐條得到裁示。未確認前，`usage_report_path` 維持 `null`，不可進入分拆 task。

---

## Step 1：列出使用者角色（who）

窮舉會觸發這個功能的所有 actor，**別只想人類使用者**。逐類檢查：

- **人類角色**：不同權限層級各算一個（例如：一般申請人 vs. 覆核主管，行為不同）
- **系統 / 排程**：cron、APScheduler job、背景 worker
- **外部系統**：webhook 回呼、上游 API、ERP 同步、訊息佇列消費者
- **維運 / 管理**：資料修補、手動重跑、稽核查詢

**檢驗問題：** 有沒有哪個 actor 是「不會主動操作，但會被這個功能的副作用影響」的？（例如下游報表、對帳程式）——它也是一個情境來源。

---

## Step 2：對每個角色展開核心情境（happy path）

每個角色在正常流程下的操作序列 + 預期結果。**每個核心情境給一個穩定 id**（見下「情境 id 慣例」）。

- 寫成「前置狀態 → 操作 → 預期結果」的序列，不要只寫一句功能名
- 一個角色可能有多條 happy path（例如「首次建立」與「後續更新」是兩條）

**檢驗問題：** 這條 happy path 能不能獨立 demo 給使用者看？不能 → 它其實是多條情境黏在一起，拆開。

---

## Step 3：找邊界 / 異常情境（最容易漏、也最值錢的一步）

對每條 happy path，逐項套下面的清單，命中就開一個新情境（沿用同一 id 家族的變體，如 A-err1）：

| 面向 | 觸發問法 |
|---|---|
| 空狀態 / 無資料 | 沒有任何資料時、第一次進來時，畫面與行為是什麼？ |
| 錯誤 / 非法輸入 | 型別錯、必填缺、格式錯時？ |
| 邊界值 | 0、負數、上限、超長字串？ |
| 併發 / race | 兩個 actor 同時操作同一筆資料？ |
| 權限不足 / 未登入 | 沒權限的角色觸發時？ |
| 外部依賴失敗 | 上游 API / DB / ERP 逾時或回錯？ |
| 部分失敗 / 回滾 | 多步驟中途失敗，已寫入的要不要退？ |
| 重複提交 / 冪等 | 同一請求送兩次？重試會不會重複扣款 / 重複建檔？ |
| 大量資料 / 效能 | 資料量放大 100 倍時？ |

**檢驗問題：** 每條 happy path 至少要問過「中途失敗怎麼辦」與「重複提交怎麼辦」——這兩個是金流 / 狀態機類功能最常見的 bug 源。

---

## Step 4：每個情境定義輸入 / 輸出契約

對**每一個**情境（含異常情境）明確寫出：

- **Input**：觸發條件、參數、前置狀態
- **預期 Output**：回傳值、狀態碼、畫面變化
- **副作用**：DB 寫入哪張表、呼叫哪個外部服務、發哪個事件 / 通知

副作用是分拆 task 時判斷「這個 item 會不會碰到高風險面（金流 / schema）」的依據，**不可省略**。

**非功能性質的 load-bearing 驗證（硬性）**：凡 Spec 或情境契約把**非功能性質**（順序、決定性、原子性、時序）列為正確性需求，必須追到**最終消費點**並附證據——「消費點 file:line ＋ 該性質被破壞時可觀察輸出如何改變」。追下去若發現下游依 key／name 重新定位（可觀察輸出不因該性質被破壞而改變），中間容器的該性質**即非需求**：從契約移除，記一行「已排除的假需求＋理由」。實測教訓：一條未驗證的保序假設讓整條 flow 為它空轉——探針 sabotage 後永遠綠（因為輸出根本不變）、mutation 反覆加時序延遲硬湊 FAIL，浪費數十輪。

---

## Step 5：標出與現有功能的互動點

- 這個功能會讀 / 寫哪些**既有模組**的資料？
- 會不會改變既有行為（回歸風險）？
- 有沒有共用的 service / 資料表需要小心不破壞其他呼叫端？

**檢驗問題：** 如果這個功能上線，有哪個**現有**功能可能因此壞掉？答不出來 → 互動點還沒盤清。

---

## Step 6：彙整開放問題（HITL gate 的核心）

把分析過程中**所有需要使用者裁示的歧義**集中成一張清單。這是報告最重要的一節——它決定了 HITL gate 有沒有價值。

每筆開放問題含：問題、你的預設傾向（tentative）、以及「若選 A vs B 對後續拆分的影響」。**不要替使用者默默假設**；攤開來讓他一次拍板。

**正確性假設清單（開放問題之外另列一節）**：本 Spec 假設「必須成立」的性質（順序、決定性、唯一性、冪等、時序），逐條列出——每條附最終消費點證據（file:line）與「被破壞時的可觀察差異」，供使用者在 HITL 逐條裁示。差異寫不出來的假設，主動標「疑似非需求，建議移除」。人打槍一條假設的成本是 30 秒；flow 為假需求空轉的成本是數十輪——這一節就是把打槍的機會攤到人面前。

---

## 情境 id 慣例（與 task-decomposition 的接合契約）

- 核心情境用大寫字母：`A`、`B`、`C`…
- 該情境的異常變體用後綴：`C-err1`、`A-edge1`
- id 一旦定下，**在報告內全程穩定**；`task-decomposition` 的每個 item 會用 `情境: <id>` 回指
- 分拆時若某情境沒有任何 item 對映 → 代表漏拆或情境多餘，回頭對帳

## 輸出格式（寫入 `usage/<run_id>.md`）

```
# 使用情境報告 — <Spec 名稱>  (run_id: <run_id>)

## 角色
- <角色1>：<一句話說明>
- <角色2>：...

## 情境
### A — <情境名>  角色: <角色>
- 前置: <狀態>
- 操作: <序列>
- 預期: <結果>
- I/O: input <...> / output <...> / 副作用 <DB 表、外部呼叫>

### C-err1 — <異常情境名>  角色: <角色>
- 觸發: <條件>
- 預期: <錯誤處理行為>
- I/O: ...

## 與現有功能互動點
- <既有模組>：<互動 / 回歸風險>

## 正確性假設清單（需使用者逐條裁示）
1. <性質，如「事件必須保序」>；消費點 <file:line>；被破壞時可觀察差異 <差異描述，寫不出差異 → 標「疑似非需求，建議移除」>
2. ...（無此類假設時寫「無」，不可省節）

## 開放問題（需使用者確認）
1. <問題>；預設傾向 <A>；若改 <B> 則 <對拆分的影響>
2. ...
```

## 反模式（要 reject 重做的報告）

- 只寫 happy path，沒有任何邊界 / 異常情境（Step 3 沒做）
- 情境沒有 id，或 id 不穩定，導致 task 無法回指
- 副作用欄空白（下游無法判斷高風險面）
- 把歧義**默默假設掉**，開放問題一節空著——等於架空了 HITL gate
- 把順序／決定性等非功能性質寫成正確性需求，卻無最終消費點證據（load-bearing 未驗證），或正確性假設清單缺節
- 報告指涉對話上下文（「如上所述」「依先前討論」）——報告必須自足，換一個 AI 讀檔即可接手
- 角色只列「使用者」一種，漏掉排程 / 外部系統 / 維運
- 報告寫成 Spec 的複述，而非「使用的視角」——沒有新增盤點價值
- 情境顆粒過粗（一個情境塞多條路徑）或過細（把單一 output 的兩個欄位拆兩個情境）

## 範例：Spec「廠商付款申請單新增部分沖銷」

> 情境 id 與 `task-decomposition` skill 範例共用，示範兩者如何接合。

**角色**
- 財務人員：對已核准申請單登記付款
- 系統（餘額計算）：依已沖銷金額更新未結餘額

**情境**

- **A — 財務登記一筆部分付款**（角色：財務）
  - 前置：一張已核准、未結餘額 > 0 的申請單
  - 操作：選申請單 → 輸入本次沖銷金額 → 送出
  - 預期：登記成功，回 201，畫面顯示更新後未結餘額
  - I/O：input `{request_id, amount}` / output `201 + 新餘額` / 副作用：寫入 `settlement` 表、更新申請單餘額

- **B — 系統更新未結餘額**（角色：系統）
  - 觸發：A 成功後
  - 預期：未結餘額 = 申請額 − Σ已沖銷；多筆部分沖銷可累加
  - I/O：input `request_id` / output `未結餘額` / 副作用：無（純計算，讀 `settlement`）

- **C-err1 — 超額沖銷被擋**（角色：財務）
  - 觸發：本次沖銷金額 > 未結餘額
  - 預期：回 422 + 錯誤訊息，不寫入
  - I/O：input `{request_id, amount(超額)}` / output `422` / 副作用：無

- **A-err1 — 併發重複提交**（角色：財務）
  - 觸發：同一申請單兩筆沖銷幾乎同時送出
  - 預期：以 advisory lock 序列化，第二筆以最新餘額重算，不得雙扣
  - I/O：副作用：需冪等 / 鎖保護

**與現有功能互動點**
- 申請單狀態機：部分沖銷後狀態應維持「核准」直到全額沖銷才轉「已結清」——動到既有狀態轉換，有回歸風險

**開放問題（需使用者確認）**
1. 全額沖銷後是否自動轉「已結清」，還是需人工確認？預設傾向「自動」；若改「人工」則需多一個情境與 item
2. 是否允許沖銷金額為 0 或負數（沖銷沖正）？預設「否」；若「是」則 C 的驗證邏輯要放寬
