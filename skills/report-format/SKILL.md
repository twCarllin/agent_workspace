# 標準化報告模板

## A. 程式碼審查報告（code-reviewer 用）

```
## 程式碼審查報告

**審查對象**：[檔案路徑或範圍]
**審查時間**：[當前時間]
**整體評分**：🟢 良好 / 🟡 需改進 / 🔴 有重大問題

---

### 重大問題（必須修正）
[問題描述，附上檔案行號]
**建議**：[具體修正方式]

### 改進建議（應該修正）
[問題描述，附上檔案行號]
**建議**：[具體修正方式]

### 優點（值得保留的好實踐）
[指出寫得好的部分，鼓勵好的習慣]

### 總結
[整體評語，3-5 句話]
```

## B. 工作報告（code-writer 用）

```
## 工作報告

### 任務摘要
[一句話描述本次任務]

### 已完成項目
- [檔案:行號] 變更描述

### 未完成項目（需人工確認）
- [原因說明]

### 建議下一步
重新執行 code-reviewer 驗證結果。
```

## C. Retro 記錄（retro 用）

RETRO.md 的消費方式是**主 flow 挑相關條目原文貼進 code-writer prompt 的硬性約束區**（eval-flow 循環 step 1），不是給人通讀——所以每條必須寫成「單獨拿出來就能當約束用」的句式，不寫敘事、不寫表格。

一條 = 一行 bullet：日期＋標籤＋背景一句＋**約束一句**（粗體，這是會被貼進 prompt 的部分）：

```markdown
- YYYY-MM-DD［標籤：模組或問題類別／來源 run_id］背景一句（發生了什麼、根因是什麼）。**約束：下次寫 X 時必須／不可 Y（具體到可執行、可檢驗）。**
```

寫作檢驗：把「約束：」之後的句子單獨貼給一個沒讀過本檔的 writer，它能照做 → 合格；需要上下文才懂 → 重寫。

## D. 任務完成度驗證報告（task-verifier 用）

```
## 任務完成度驗證報告

**任務**：[任務編號 — 任務標題]
**驗證時間**：[當前日期]
**判定**：🟢 通過 / 🟡 有條件通過 / 🔴 未通過

---

### 子任務完成度
| # | 子任務 | 狀態 | 證據 |
|---|--------|------|------|
| 22-1 | [描述] | ✅ 完成 / ❌ 遺漏 / ⏭️ 刻意跳過 | [diff 行號或 grep 結果] |

### DoD 逐條驗證
| # | 驗收標準 | 通過 | 證據 |
|---|---------|------|------|
| 1 | [標準描述] | ✅ / ❌ / 🔍 需人工驗證 | [具體證據] |

### Scope 偏移
- [列出 diff 中有改但 task 沒提到的檔案/區域]
- [列出 task 提到但 diff 中沒改的檔案/區域]
- [「不做的事」違反檢查結果]

### 技術限制遵守
- [逐一列出 task 中標註的限制，確認是否遵守]

### 總結
[整體評語：完成度百分比、遺漏項目、需要人工確認的項目]
```
