# Bug 診斷紀律

收件人：**主 flow** 或執行診斷的 agent（具 Bash／Read／Edit 權限）。各 Phase 不可跳過，除非明文寫出理由。

判級規則與 BUGLOG append 格式見 CLAUDE.md「工作型態前判」節，本 skill 只管診斷方法。

---

## Phase 1 — 建立回授迴圈

**這是整個診斷的核心。** 有緊繃的紅／綠訊號，後面的假設驗證與插樁才有依附點；沒有，再多的 code 閱讀也找不到根因。**此命令不存在前，禁止進入假設階段。** 「先讀 code 建理論」正是本 skill 要防的失敗模式。

### 可試的構造方式（依序嘗試）

1. **失敗的測試**：在能觸及 bug 的最近 seam（unit／integration／e2e）
2. **curl／HTTP script**：對執行中的 dev server 打，斷言回應
3. **CLI 呼叫 + fixture 輸入**：diff stdout 與 known-good snapshot
4. **無頭瀏覽器腳本**（Playwright／Puppeteer）：驅動 UI，斷言 DOM／console／network
5. **重放捕獲的 trace**：把真實 request／payload 存檔後用 script 重放
6. **拋棄式 harness**：最小子系統（一個服務、mocked 外部依賴），單一函式呼叫觸發
7. **屬性／fuzz 迴圈**：跑 1000 組隨機輸入找失敗
8. **bisection harness**：兩個已知狀態之間自動切換 + 判定

### 完成判準（硬性 checklist）

Phase 1 完成 = 能指名**一條命令**（測試呼叫／curl／script 路徑），已**實跑至少一次**（記下指令與輸出），且同時滿足：

- [ ] **會紅**：驅動實際 bug 路徑、斷言使用者描述的症狀；「沒有 crash 即算過」不符合
- [ ] **確定性**：每次跑同判定。非確定性 bug 改目標為「已拉高且釘住重現率」，手法：迴圈觸發 100 次、平行化、加壓、縮時窗；50% 重現率可調試，1% 不行
- [ ] **快**：秒級
- [ ] **agent 可自跑**：不需人工介入

### 真的建不出迴圈時

明說、列出已試過的方法，向使用者要：（a）能重現的環境存取、（b）去除機密的捕獲工件（HAR、log dump、core dump）、（c）加臨時生產插樁的許可。**不可在無迴圈下進入 Phase 2。**

---

## Phase 2 — 重現與最小化

跑迴圈，看它轉紅。確認：

- 失敗模式符合**使用者描述的症狀**，不是鄰近的另一個錯誤
- 重現穩定（或重現率已拉到可調試水準）
- 已記下精確症狀（錯誤訊息、錯誤輸出、時序）供 Phase 5 對比驗收

### 最小化

迴圈轉紅後逐項削減：輸入、呼叫端、設定、資料。**每削一項就重跑迴圈**，只保留削掉後會轉綠的元素。

**完成判準：每個殘留元素都承重——再削任一項就轉綠。**

最小化的雙重回報：假設空間縮小（Phase 3 移動部件少）；最小化情境直接成為回歸測試素材。

---

## Phase 3 — 假設

一次列 **3–5 個假設**，排名後才開始驗任何一個。單一假設會錨定，不給第二個機會浮現真正的根因。

每個假設**必須可否證**，固定格式：

> 若 X 是根因，則改 Y 後 bug 消失／改 Z 後惡化。

寫不出預測句的不算假設，捨棄或再磨尖。

**先向使用者回報排名清單再開驗。** 使用者往往有「剛部署過 #3」這類內部知識，可立刻重排；使用者不在場則按自排名繼續，不阻塞。

---

## Phase 4 — 插樁

**每次只改一個變數。** 每個探針對應 Phase 3 的一個具體假設。

工具優先順序：
1. **debugger／REPL**：一個斷點勝過十條 log
2. **針對性 log**：只在能區分假設的邊界打
3. **禁止「log 全部再 grep」**

**所有 debug log 加唯一前綴**，格式：`[DEBUG-<4位隨機碼>]`（例：`[DEBUG-a4f2]`）。理由：收尾清理是一次 grep，不是逐行找。

**效能問題另法**：log 通常是錯的工具。先建立基線量測（timing harness、profiler、query plan），用 bisect 定位，不靠 log 推斷。

---

## Phase 5 — 修法與收尾

### 先寫回歸測試再修

在**正確 seam** 寫回歸測試，讓它轉紅，再動修法，讓它轉綠，最後用**原始未最小化情境**重跑 Phase 1 迴圈確認。

**找不到正確 seam 時，「無 seam 本身就是發現」**：寫入診斷結論，不硬塞假信心測試。錯誤 seam 上的測試（如單呼叫端測試無法複現多呼叫端觸發的 bug）給假安全感。

### 收尾 checklist

- [ ] 用**原始情境**重跑 Phase 1 迴圈，確認轉綠
- [ ] `grep [DEBUG-<你用的碼>]` 確認所有 debug log 已清
- [ ] 拋棄式 harness 已刪（或移到明顯標記的 debug 位置）
- [ ] 正確假設已寫進 commit message（讓下一個調試者知道根因）

### 診斷結論（固定三行）

```
根因：<一句>
影響面：<一句>
修法：<一句>
```

此三行即後續判級的 `spec_inline`，帶入 CLAUDE.md「工作型態前判」流程。
