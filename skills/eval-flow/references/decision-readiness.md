# Spec 就緒、決策與 HITL

本文件是 Tier 1／2 前置、拆解與交接的共用判斷。Tier 1 在既有需求／task 補缺口即可；Tier 2 寫入 Spec。既有資料可引用，不新增固定報告或審查輪次。

## 可接手的規格

接手者須能從需求與引用資料判定下列內容；缺少且影響實作或驗收時才補充：

- **結果**：使用情境、預期可觀察行為及 DoD。
- **邊界**：修改範圍、不做事項，以及本次相關的相容要求與失敗行為。
- **已定決策**：採用選項、理由、裁決來源及適用範圍。使用者裁決與 agent 的工程選擇須分清楚。
- **決策權限**：已授權的工程選擇，以及仍需使用者決定的產品行為或操作。缺少明示限制不等於新增授權；按目前 session 授權與既有硬性規則判斷。

拆解者或接手者只讀以上資料，檢查能否確定預期行為、執行範圍與驗證方式。缺口寫成「缺哪項決策／事實、阻擋哪個 item、無法判定哪個結果」，交主 flow 處理；不以「Spec 不完整」要求全面重寫。主 flow 直建 task 時做相同核對，不因此固定另派 agent。

## 提問前的判斷

1. **查既有決策**：先讀相關 Spec、task 與裁決來源。已決事項沒有新證據或新的使用者指示，就沿用；換 agent、換 session 或重新拆 task 都不是重問理由。
2. **確認可自行決定的範圍**：已授權範圍內、不改產品契約且不觸必要授權的工程選擇，由 agent 決定；影響接手的選擇記回規格。可用 Git 還原本身不構成產品取捨的授權。
3. **調查可查證的事實**：程式、文件、查詢或驗證能回答的問題先調查。未知或 `［假設］` 不自動成為 HITL；未證實者仍標未知，不能當成事實。若必要資料／權限無法取得，記明已查來源、缺口與阻擋範圍，才請使用者補足。
4. **集中需要裁示的問題**：業務事實、產品偏好、需求多義或授權不足且前述方法不能解決時，才向使用者提出。每題附具體問題、可行選項、建議及理由（無足夠依據則明說）、影響與阻擋範圍；同階段已知問題合併提出，不為收集全部未知而延後必要提問。

子 agent 將缺口交主 flow；主 flow 核對既有資料後再決定是否 HITL。取得答案後先寫回規格，更新受影響的 task／契約及交接內容，再開始依賴該答案的實作。答案使計畫變動時，更新計畫；只有新增需裁示事項或原確認範圍已不涵蓋變更時，才再次提問。

## Full-send：單次任務的工程決策委託

使用者對一個明確任務要求「full-send／full send」或明示「工程決策由你處理，完成後回報」時適用。引用、研究或討論名稱不啟動。開始時在既有 task／Spec 記錄授權原文、任務範圍與交付終點；依原請求判定，不因名稱增加 push、PR、合併、部署或資料刪除授權。缺少任務才詢問，不為已明確的終點再確認。本節優先處理該任務的工程選擇；Router 的預設採納模式仍適用其餘問題。

- **自行決定**：實作方法、檔案安排、適用測試、缺陷修法及滿足相同契約的方案，由主 flow 查現有慣例與證據後裁決；同等可行時選整體成本較低、容易還原的方案。依 CODE_QUALITY 的複雜度判準保留必要保證。重要決策記在既有 task／Spec，收尾摘要回報，不為每個局部選擇增加表單。
- **爭議先取證**：給未解問題穩定識別，記錄需求依據、雙方主張、證據與處置。先重現或查相關原始來源；有證據即可按契約裁決，必要獨立審查仍須獨立重裁。不能只因 reviewer 不同意就交使用者選邊，也不能由作者把未解審查改成通過。只有錯誤前提持續造成無效往返或缺少所需專長時，才換獨立審查者；保留全部未解問題與已用次數。
- **有限恢復**：適用的修正上限到達時，停止原修法；本模式每個 task 至多增加一次主 flow 診斷，整理具體失敗、已試方法、有效證據與待驗假設。僅有新證據支持不同修法、且仍在授權範圍內時，可再修正一次並完成必要驗證與獨立重審。此額度涵蓋該 task 全部問題，不因換 agent、改問題名稱或恢復 session 重置；診斷無新證據或追加修正仍未解時，停止受影響工作並回報具體阻礙。這是 review.md 修正上限的唯一例外，不放寬 writer 自驗上限或其他 gate。
- **需要使用者**：只有使用者掌握的業務資訊、會改變結果的產品取捨、授權缺口或無法取得的必要外部資源，依前節集中提問。具體說明已查證據、阻擋項目與最少需要的協助。技術受阻時回報診斷與缺少證據，不要求使用者代選尚未查證的工程修法；證據不足不宣稱完成。
- **持續與停止**：依原授權完成全部實作、驗證、適用審查及交付；可以獨立推進的工作繼續。使用者要求停止時立即停止。必要 gate、工具權限與驗證標準照常；不得把沉默、輪數用完或 full-send 當成 gate 通過。已明確授權的同一操作不重問；尚未取得的必要 Tier 2 計畫確認不得自行填寫。
- **恢復與交付**：委託隨該任務保留，恢復時核對原文、目前範圍、已用額度與證據；新需求不繼承。完成、取消或使用者撤回後失效。若原請求含遠端交付，本地 run 完成後仍須繼續至指定終點，保存剩餘操作及實際遠端結果，不以本地 commit 代表 PR 已就緒或已合併。最終回報結果、重要自主決策、驗證與未解限制。

## 執行期間與必要 gate

新事實推翻決策時，列出新證據、原決策位置及受影響範圍，再依上述判斷處理。局部問題先停止受影響 item 及其相依項目；其他 item 只有在已授權、依賴已滿足且符合既有 staging、審查、worktree 隔離與排程規則時才可繼續。不得以局部受阻為由，在同一工作區另開 run 或跳過未完成 task 的審查。重大風險或 Router 升級條件成立時，仍依原規則停止／升級。

Tier 2 與舊 run 的計畫確認、部署／對外操作授權、驗證豁免及其他必要 HITL 仍依原規則。共用判斷用來準備問題，不代替使用者裁示，不自行開啟預設採納模式；等待時間、使用者未回覆或 headless 執行均不算授權。

## HITL 留痕與改善

實際提問時，在既有 task 備註記一筆「問題｜原因｜阻擋範圍｜已查來源｜裁決位置／待答」。task 尚未建立時先記在 Spec，之後引用即可；不重複保存答案。必要確認而無決策缺口者記「必要 gate」，與可避免中斷分開。

決策缺口的原因依實際情況記為 **Spec 缺口／交接遺失／授權不清／新事實**；可有多項，不因分類取代調查。收尾回看重複提問及可避免中斷，將具體規則問題列為改善候選；若既有規則重複或無效，先核對其保證與證據再合併或移除，不直接追加通用限制。不為蒐集指標增加 HITL，也不把尚未量測的減量宣稱為成果。
